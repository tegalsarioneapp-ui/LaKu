PROMPT REFACTOR BERTAHAP
ALUR PENGAJUAN DANA OPERASIONAL RT
============================================================

Tujuan:
Melakukan refactor aplikasi secara bertahap berdasarkan task.
Setiap task harus dikerjakan, diuji, dan divalidasi terlebih dahulu
sebelum melanjutkan ke task berikutnya.


KONTRAK BISNIS UTAMA
============================================================

1. 7 dokumen hanya untuk Pengajuan Awal Dana, satu kali per tahun.
2. Dana Rp25.000.000 masuk ke rekening BPD atas nama RT satu kali.
3. RAP dibuat untuk satu tahun dan dibagi ke kegiatan bulanan.
4. Setiap bulan hanya ada satu dokumen:
   "Pengambilan Operasional RT Melalui Bank BPD Jateng".
5. Satu bulan hanya boleh memiliki satu record pengambilan.
6. Pengambilan bulan berikutnya mensyaratkan LPJ kegiatan yang selesai
   pada bulan sebelumnya sudah lengkap.
7. Pengambilan pertama menjadi pengecualian karena dana awal baru masuk
   rekening.
8. Renderer lama, ID lama, sinkronisasi, dokumen, dan data existing
   harus tetap kompatibel.
9. Refactor dilakukan bertahap, bukan menulis ulang seluruh aplikasi.
10. Draft pengambilan boleh dibuat saat LPJ belum lengkap, tetapi
    finalisasi dan cetak final harus diblokir.

============================================================

Kerjakan hanya task yang saya berikan sekarang.

Jangan mengerjakan task berikutnya, jangan melakukan refactor besar
di luar scope, dan jangan menghapus renderer lama, ID lama,
localStorage existing, atau data pengguna.

Sebelum mengubah kode:

1. Baca replit.md jika tersedia.
2. Baca .agents/memory/MEMORY.md dan topic yang relevan.
3. Periksa git status.
4. Cari implementasi existing dengan rg atau grep.
5. Pahami hubungan antara frontend, API, localStorage, PostgreSQL,
   renderer dokumen, dan sinkronisasi.

Pertahankan kompatibilitas backward dengan data yang sudah ada.

Setelah selesai:

1. Jalankan syntax check.
2. Jalankan type check, build, dan test yang tersedia.
3. Jalankan git diff --check.
4. Laporkan file yang berubah.
5. Laporkan risiko atau hal yang belum dikerjakan.
6. Jangan lanjut ke task berikutnya.

3. Setelah status approved atau disbursed, data tidak boleh
   diam-diam dibuat ulang.

   idempotent.
5. Jangan menghapus atau mengganti data pengajuan lama.
6. Jangan mengubah renderer dokumen lama pada task ini.
7. Jangan membuat proses pengambilan bulanan dulu.

Jika struktur data terbaik berbeda dari nama yang disebutkan di atas,
ikuti pola existing aplikasi, tetapi tetap pisahkan konsep:

- pengajuan awal,

Tambahkan test untuk:

- data baru,

Kerjakan hanya model data dan migrasi dasar.

Kriteria selesai:

- Data existing tetap bisa dibaca.
- Migrasi aman dan idempotent.
- Pengajuan awal memiliki status dan identitas tahun.
- Belum ada perubahan pada alur bulanan.

Tambahkan test untuk:

- checklist belum lengkap,
- checklist lengkap,

TASK 03 — RAP TAHUNAN DAN KEGIATAN BULANAN
============================================================

Kerjakan TASK 03 — Tegaskan RAP Tahunan sebagai sumber kegiatan
bulanan.

Gunakan data RAP existing dan struktur aplikasi saat ini.

Aturan:

1. RAP memiliki tahun anggaran.
2. Setiap item RAP minimal memiliki:
   - uraian kegiatan,
   - kategori,
   - bulan pelaksanaan,
   - nominal,
   - volume/satuan jika sudah didukung,
   - keterangan,
   - status.
3. RAP tahunan dapat dibagi ke beberapa bulan.
4. Total RAP tidak boleh melebihi Rp25.000.000.
5. Jangan mengubah arti data RAP existing secara destruktif.
6. Jika ada format RAP lama, buat normalisasi atau adapter.
7. Setiap kegiatan harus memiliki identitas stabil agar dapat
   dihubungkan ke:
   - LPJ,
   - foto MoKu,
   - dokumen SPJ,
   - pengambilan bank bulanan.
8. Kegiatan yang tertunda tidak boleh langsung dianggap selesai.
9. Kegiatan yang selesai harus memiliki tanggal realisasi.
10. Jangan membuat dokumen pengambilan bank pada task ini.

Perbaiki validasi dan tampilan RAP agar pengguna dapat melihat:

- total RAP tahunan,
- total per bulan,
- sisa alokasi,
- kegiatan yang belum memiliki bulan,
- kegiatan yang belum memiliki nominal.

Pertahankan loader RAP, renderer legacy, dan kompatibilitas data lama.
Tambahkan test perhitungan total tahunan dan bulanan.

Kriteria selesai:

- RAP menjadi sumber resmi kegiatan.
- Total RAP tervalidasi terhadap Rp25.000.000.
- Setiap kegiatan memiliki ID stabil.
- Data RAP dapat digunakan oleh task LPJ dan pengambilan bulanan.


TASK 04 — KEGIATAN DAN LPJ PER AKTIVITAS
============================================================

Kerjakan TASK 04 — Tambahkan siklus LPJ per kegiatan.

Gunakan kegiatan yang berasal dari RAP pada TASK 03.

Setiap kegiatan harus memiliki status LPJ:

- not_started
- in_progress
- uploaded
- needs_revision
- verified

Tambahkan atau sesuaikan model LPJ agar dapat menyimpan:

- activityId,
- bulan kegiatan,
- tanggal selesai,
- status LPJ,
- daftar file atau bukti,
- catatan pemeriksa,
- tanggal upload,
- tanggal verifikasi.

Bukti LPJ harus terhubung ke kegiatan tertentu. Jangan hanya menyimpan
satu checklist global untuk semua kegiatan.

Jika aplikasi belum memiliki upload file lengkap, buat adapter/interface
yang mengikuti pola penyimpanan existing. Jangan mengganti sistem
storage tanpa audit dan tanpa alasan.

Aturan:

1. Kegiatan yang belum selesai belum wajib memiliki LPJ final.
2. Kegiatan yang sudah selesai wajib memiliki LPJ lengkap.
3. Status checkbox tidak boleh dianggap sama dengan file sudah di-upload
   jika sistem mendukung upload.
4. Tampilkan kegiatan yang masih memiliki kekurangan.
5. Pertahankan integrasi foto MoKu dan renderer dokumen lama.
6. Jangan membuat gate pengambilan bulan berikutnya pada task ini;
   hanya siapkan fungsi pemeriksaan kelengkapan LPJ.

Tambahkan fungsi pemeriksaan yang mengembalikan:

- apakah LPJ bulan tertentu lengkap,
- jumlah kegiatan belum lengkap,
- daftar kegiatan yang bermasalah,
- alasan kekurangannya.

Tambahkan test untuk:

- kegiatan selesai,
- kegiatan tertunda,
- LPJ kosong,
- LPJ lengkap,
- LPJ perlu revisi.

Kriteria selesai:

- LPJ terhubung ke activityId.
- Status LPJ jelas.
- Sistem dapat menghitung kelengkapan LPJ per bulan.
- Daftar kegiatan bermasalah dapat ditampilkan.


TASK 05 — PENGAMBILAN OPERASIONAL SATU RECORD PER BULAN
============================================================

Kerjakan TASK 05 — Implementasikan Pengambilan Operasional bulanan.

Gunakan RAP dari TASK 03 dan pemeriksaan LPJ dari TASK 04.

Dokumen bulanan yang digunakan hanya:

"Pengambilan Operasional RT Melalui Bank BPD Jateng"

Aturan wajib:

1. Satu tahun dan satu bulan hanya boleh memiliki satu record
   pengambilan.
2. Gunakan kunci unik berbasis tahun anggaran dan bulan.
3. Jika record sudah ada, buka record yang sama, jangan membuat duplikat.
4. Record pengambilan terhubung ke kegiatan RAP pada bulan tersebut.
5. Nominal pengambilan berasal dari kegiatan/anggaran bulan tersebut.
6. Pengambilan mengurangi saldo dana awal Rp25.000.000.
7. Pengambilan bukan pencairan dana baru.
8. Pengambilan pertama adalah pengecualian dari gate LPJ bulan sebelumnya.
9. Pengambilan bulan berikutnya hanya boleh difinalisasi jika LPJ
   kegiatan yang selesai pada bulan sebelumnya lengkap.
10. Draft boleh dibuat, tetapi finalisasi/cetak final harus diblokir
    jika LPJ belum lengkap.
11. Tampilkan alasan pemblokiran dan daftar kegiatan yang LPJ-nya kurang.
12. Jika tidak ada kegiatan selesai pada bulan sebelumnya, gate LPJ
    dianggap terpenuhi.
13. Jangan membuat 7 dokumen pengajuan pada proses ini.
14. Pertahankan renderer dokumen Pengambilan Bank existing jika ada.

Status minimal:

- draft
- blocked_by_lpj
- ready
- finalized
- cancelled

Tambahkan API atau local persistence sesuai pola existing.
Jangan membuat data ganda antara frontend, API, dan PostgreSQL.
Pastikan sync multi-device tetap aman.

Tambahkan test:

- record pertama,
- duplicate bulan,
- draft saat LPJ belum lengkap,
- finalisasi saat LPJ lengkap,
- finalisasi saat LPJ belum lengkap,
- bulan tanpa kegiatan selesai,
- saldo setelah pengambilan.

Kriteria selesai:

- Satu bulan hanya memiliki satu dokumen pengambilan.
- Gate LPJ aktif sebelum finalisasi.
- Pengambilan pertama dapat diproses.
- Pengambilan tidak dihitung sebagai pencairan dana baru.
